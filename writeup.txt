Vulnerability Summary
• A phase in the DFG JIT compiler, StoreBarrierInsertionPhase,
erroneously omits the insertion of a StoreBarrier.
• The missing StoreBarrier allows a live object to be prematurely
freed by concurrent GC under a race condition, resulting in a useafter-free.

Tri-color Invariant
• Let's review the color state of an object:
White: Not marked yet (liveness not yet established)
Grey: Marked as reachable but whose outgoing references have not yet
been scanned
Black: Marked as reachable and fully scanned
• Tri-color Invariant: Black -> White
• A white object may not have been discovered yet.
• If a black object points to a white object, the white object may be missed
by the marker.
• The white object could be incorrectly reclaimed while still being reachable.
• => Potential Use After Free
• Takeaway: Black -> White => Potential Use After Free
14
Store Barrier
• Motivation: Prevent Black -> White from happening.
• Typical Example: o1.p = o2
• PutByOffset(o1, o2, "p")
• StoreBarrier(o1)
• StoreBarrier(o1) notifies the GC that o1 may need to be
rescanned due to a newly introduced reference.
• Common Implementation: Color(o1) = Grey

Virtual Storage Slot
• In SSA, values are explicit, but their storage locations are not.
• While SSA is well-suited for reasoning about value flow, compiler
optimizations that affect memory correctness must also reason about where
values are stored, especially across control-flow merges.
• To precisely capture this notion, we introduce Virtual Storage Slot (VSS) -
an abstract representation of a logical heap storage location into which SSA
values may be written.

Upsilon Node
• To reduce the implementation complexity of Phi nodes, Upsilon nodes
are introduced to represent writes of SSA values into a Virtual Storage
Slot along specific control-flow edges in JSC.

Semantic Gap between JIT Compiler & GC
• Recap: One commonly used heuristic for inserting a StoreBarrier
when establishing a points-to relationship is whether the pointee
object is considered GC escaping.
• However, the JIT compiler operates only on abstract SSA values,
control flow, and IR-level abstractions, rather than concrete runtime
objects and their GC escaping attributes.
• As result, GC escaping must be approximated from each abstract
SSA value instead of being directly observed at runtime.
• The vulnerability arises precisely from this semantic mismatch
between SSA-level reasoning and GC’s runtime observation model.
• Takeaway: Runtime objects aren't in a 1:1 correspondence with SSA
values alone.
25
Virtual Storage Slot: Bridging SSA and GC Semantics
• If SSA values do not uniquely correspond to runtime objects, what does?
• Virtual Storage Slot (VSS).
• A unique runtime object resides in a fixed VSS, regardless of how many SSA
values represent it.
• Runtime GC observes storage locations, not SSA values.
• GC escaping attribute should be made per Virtual Storage Slot instead
of per SSA value.
