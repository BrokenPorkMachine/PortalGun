# Captive-portal LAN self-check — modular edition

One endpoint that tests **every device on your own network** against a catalog
of security checks. Each check is a **drop-in module**: copy the template into
`portal/modules/`, fill in a manifest + a page, and it shows up on the landing
page — **no server rebuild, no restart**. 110 modules are installed (see
catalog). The catalog page has a text + tier filter once the count gets long.

## Module tiers

| tier | meaning | what the module does |
|---|---|---|
| **1** | full public PoC exists | runs the reproducer's **detection stage only** — address leak, silent trigger, or crash oracle. No exploit chain is ever shipped. |
| **2** | root cause public, browser-page PoC not | probe reconstructed from the published analysis + divergence oracle — clearly marked as reconstructed, and the page says a negative is weak evidence |
| **3** | advisory only | engine fingerprint + version report, links to bug/CVE/advisory. **No exploit code** — honest "no public PoC" (98 modules generated by `tools/mkadvisory-modules.py`) |

A note on what tier 1 means here: several of the public PoCs are complete
chains that end in RWX shellcode (`saelo/jscpwn`, `BadAccess11/CVE-2019-8601`,
`Billy-Ellis/jitsploitation`, `saelo/cve-2018-4233`). Those modules run the
*oracle* half of the PoC — the part that answers "is this device vulnerable?" —
and stop before any privilege-building. That is the same line the pre-existing
tier-1 modules draw.

## Crash oracle (tier-1 crash PoCs)

For bugs whose public PoC is "crash the renderer", the page dying *is* the
signal. `LanCheck.start({ crashOracle: true })` gives a module:

- a localStorage marker (`lc-crash-<module>`): left as `running` if the
  renderer died mid-run; the **next load** of that module page reports
  `crash` immediately;
- a 1 Hz heartbeat (`alive` events); the server marks a device whose last
  event is a stale heartbeat (>45s) as `crashed (renderer died)`.

The dashboard paints both signals red.

## Adding a check (drop-in)

```sh
cp -r portal/modules/_template portal/modules/CVE-YYYY-NNNNN
$EDITOR portal/modules/CVE-YYYY-NNNNN/module.json   # title, CVE, engine, affected…
$EDITOR portal/modules/CVE-YYYY-NNNNN/index.html    # LanCheck.start({ run: … })
# refresh the landing page. that's it — the catalog rescans every request.
```

Rules: folder name = module id (prefix `_` hides a module), `module.json` must
be valid JSON, check lives in `index.html` via `LanCheck.start({ module,
presets, run })`. Add `"tier": 1|2|3` to the manifest.

### Manifest fields (`module.json`)

`id`, `title`, `cve`, `engine`, `platform`, `category`, `severity`, `summary`,
`affected`, `fixed`, `proof`, `presets`, `source`, `tier`.

### Module API (`run(ctx)`)

`ctx` provides `cfg` (selected preset), `log(msg, cls)`, `progress(n)`,
`report(event, detail)`, `aborted()`, `expired()` (wall-clock cap), `tick()`
and `sleep(ms)`. Return `{ outcome, detail, html? }`; outcome ∈
`vulnerable` / `vulnerable-class` / `patched` / `no-uaf` / `aborted` /
`advisory` / `unknown`.

## Regenerating tier-3 modules from advisories

```sh
python3 portal/tools/mkadvisory-modules.py --dry-run   # list
python3 portal/tools/mkadvisory-modules.py             # write
python3 portal/tools/mkadvisory-modules.py --only WSA-2026-0006   # one advisory
```

Sources transcribed in the script: WebKitGTK/WPE advisories **WSA-2026-0001**
(2026-03-18) through **WSA-2026-0006** (2026-09-29), plus Ubuntu **USN-7957-1**
(2026-01-13). Add entries to the matching list in the script; it rewrites
manifests + pages and validates each manifest as JSON. The `--only` filter
regenerates a single advisory — handy when one WSA lands and you don't want
to touch the rest.

Each module's "References" line points at the advisory it came from, so a page
never claims a CVE is in the wrong advisory.

### What is deliberately *not* generated

**WSA-2026-0006 also lists ~200 Chromium-bundled Skia/ANGLE CVE IDs** ("… in
Google Chrome prior to …"). Those are skipped on purpose. A WebKit engine
fingerprint taken from a device on your LAN says nothing about a Skia bug that
ships inside Google Chrome — those modules would look thorough while reporting
nothing. Only the 21 WebKit-native entries (the ones carrying `Credit to …` and
a `WebKit Bugzilla` reference) are transcribed.

Same reasoning applies to **CVE-2024-4367** (a PDF.js entry in WSA-2026-0004
with no WebKit bug): it is included, but its module says plainly that the
vulnerable code is the PDF.js font path, not the engine you are fingerprinting.

## Regenerating tier-1/2 modules from public PoCs

```sh
python3 portal/tools/mkpoc-modules.py --dry-run   # list
python3 portal/tools/mkpoc-modules.py             # write
```

Every tier-1/2 module is generated from `tools/mkpoc-modules.py`, which holds
the metadata and the `run(ctx)` body per CVE plus the URL of the public PoC it
came from. Regenerating is idempotent.

### Testing a generated module before you trust it

```sh
node portal/tools/checkmodules.js CVE-2016-4622   # parses + structural check
node portal/tools/testrun.js   CVE-2016-4622     # executes run(ctx) on a stub DOM
```

`testrun.js` loads the page's sibling scripts in the **order the page
references them** (order is load-bearing: `int64.js` builds `Int64.Zero` at
parse time and needs `unhexlify()` from `utils.js`), stubs `document` /
`Worker` / `history` / WebGL, then calls `run(ctx)` and prints the outcome.
Anything that throws, hangs, or returns a nonsense outcome shows up here.

### Bugs the harness caught during development

Worth knowing, because they are the failure modes that matter:

- **A false-positive verdict.** The first `CVE-2018-4233` probe reported
  `vulnerable-class` on every engine, including this one, because it treated
  "the `lastIndex` `valueOf` callback ran" as the bug. That is spec-mandated
  behaviour, not a bug. It now only fires when the cold and warm runs of the
  *same sequence* disagree.
- **An inverted verdict.** The first `CVE-2019-8601` probe counted a thrown
  read as evidence of the overflow. Throwing is what a *correctly sized*
  butterfly looks like when a walk runs off the heap. A refused materialisation
  is now the patched signal.
- **A hang.** `CVE-2023-28205` waited the full preset cap when the worker never
  answered. It now has a 15s grace and reports `unknown` (*UNTESTED*) rather
  than sitting there.
- **A load-order bug.** `int64.js` before `utils.js` threw `unhexlify is not
  defined` on every load.

## Scope rules (read first)

- **Only devices you own or are explicitly authorized to test.** If guests,
  employees or neighbors can reach the portal, don't run it.
- Modules are proof-level. Nothing escalates to code execution, by design.
- The **token** (`PORTAL_TOKEN`) gates every report; reports without it get 403.
- Tier-3 modules run no exploit code — they only fingerprint the engine.
- Tier-2 negative verdicts are *unknown*, not *patched*. A probe that does not
  diverge has not proven the engine fixed — see the tier-2 table.

### On vendored third-party code

`CVE-2016-4622` ships `utils.js` + `int64.js` verbatim from `saelo/jscpwn`
(MIT-style research code, browser-safe: no shell builtins, no `require`). They
are upstream files, not rewritten, and the module notes say so on the page.
`src` in the manifest points at the originating repo, not at a mirror.
